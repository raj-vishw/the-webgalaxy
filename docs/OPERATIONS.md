# Operations

How to run The WebGalaxy in production: deployment shape, configuration, database care, monitoring, and the security checklist.

## Vercel

The repository also deploys as a single Vercel project: static site plus one Node.js
Function at `api/index.ts` that wraps the same Fastify app (`vercel.json` rewrites
`/api/*` and `/health*` to it and everything else to `index.html`). Migrations run on
the function's cold start; seed the production database once with
`DATABASE_URL=… npm run db:seed`. See the README's "Deploying to Vercel". The build also prerenders one static HTML page per universe and website for crawlers (README, *Production*); `vercel.json` sets `cleanUrls` so they answer at the same paths as the deep links, and `VITE_SITE_URL` only needs setting when the canonical origin is not the project's production domain.

## Topology

Independently deployable parts:

| Part | Artifact | Where |
| --- | --- | --- |
| Public galaxy | `dist/` (static) | any static host / CDN with SPA fallback (`/*` → `index.html`) |
| API | `backend/dist/` (`node backend/dist/server.js`) or the `backend/Dockerfile` image | a Node host or container platform, behind TLS |
| Database | PostgreSQL 15+ | managed PostgreSQL or `docker compose up db` |

The public app talks to the API at `VITE_API_URL` (build-time). Same-origin (`/api` reverse-proxied to the API) avoids CORS entirely; otherwise list the web origin in `CORS_ORIGINS`.

## Configuration

All configuration is environment variables (`backend/.env.example`). Production hard requirements enforced at startup: `NODE_ENV=production`, `DATABASE_URL`, a real `JWT_SECRET` (`openssl rand -hex 32`) and real credentials (see `backend/.env.example`). Recommended: `TRUST_PROXY=true` behind a proxy, `LOG_LEVEL=info`, rate limits tuned to expected traffic (`RATE_LIMIT_GLOBAL`, `RATE_LIMIT_SEARCH`, `RATE_LIMIT_SUBMIT`).

Rotate `JWT_SECRET` to invalidate every session.

## Database

- **Migrations** live in `backend/drizzle/` and are applied on API start (`migrate()` in `server.ts`) and by `npm run db:migrate`. They are additive SQL files generated by drizzle-kit; review each before deploying.
- **Seeding** (`npm run db:seed`) upserts the built-in catalogue (curated + `src/data/directory.ts`) by slug; regenerate the directory layer with `npm run import:curlie` after refreshing the dumps under `content/`, then `npm run logos` to refresh the icon atlases in `public/logos/` (see the README's *Catalogue data*). It is safe to re-run and finishes in seconds even against a hosted database (rows go in batches, not one round-trip per website); `--reset` truncates everything first and, against a remote PostgreSQL, additionally requires `--yes`; `--prune` removes universes that are no longer in the catalogue together with their websites (without it the seed only reports them). Never run the seed against PGlite while the API holds the same directory open.
- **Indexes**: slugs and normalised URLs (unique), `websites(universe_id, is_active)`, trending/emerging flags, relationship source/target, tag links, and a GIN index on the generated `search_vector` (name + description) that search uses alongside ILIKE.

### Backups

The database is the source of truth and is not disposable.

- **Frequency**: daily logical backups (`pg_dump -Fc "$DATABASE_URL" > webgalaxy-$(date +%F).dump`) plus point-in-time recovery / continuous WAL archiving if the managed provider offers it. Keep at least 14 daily and 3 monthly copies, off the database host.
- **Before every deploy that ships a migration**: take a backup first.
- **Restore**: `pg_restore --clean --if-exists -d "$DATABASE_URL" webgalaxy-YYYY-MM-DD.dump`, then start the API (it applies any migrations newer than the dump). Verify with `GET /health/ready`, `GET /api/universes` and an sign-in.
- **Test restores** quarterly into a scratch database.
- Uploaded assets do not exist in this version (logos are URLs), so the database backup is the complete state.

## Health & monitoring

- `GET /health` — liveness (process up). Use for load-balancer checks.
- `GET /health/ready` — readiness (database answers) — 503 otherwise. Use for deployment gates.
- Logs are structured JSON (pino) on stdout: request failures (status ≥ 400), authentication failures, authorization denials, management actions, submission events, unexpected errors. Ship them to your log platform; alert on `level >= 50` (error) and on rising 429/5xx rates.
- Error monitoring: add a provider inside `registerErrorHandler` (`backend/src/middleware/errorHandler.ts`) — every unexpected error passes through that one function.
- Frontend analytics are abstract (`src/lib/analytics.ts`): install a provider with `setAnalyticsProvider` to receive `galaxy.entered`, `universe.selected`, `website.selected`, `search.performed`, `discovery.started/completed`, `external_site.opened`, `submission.created`. Nothing personal is included.

## Security checklist

- Public API is read-only except `POST /api/submissions`, which is rate limited, validated (Zod + database constraints), duplicate-checked on a normalised URL, honeypot-protected, and never publishes without moderation.
- Content management requires a JWT (`Authorization: Bearer`) and is enforced server-side regardless of what any UI shows. No cookies are used, so CSRF does not apply. Visitors never sign in.
- Passwords: scrypt with per-password salt. Tokens expire (`JWT_EXPIRES_IN`). Logs redact authorization headers, passwords and tokens.
- URLs: only public `http(s)` hosts with a real hostname; `javascript:`, `data:`, credentials, private/loopback hosts are rejected. "Visit Website" opens with `noopener,noreferrer` in a new tab; nothing is embedded in iframes and no submitted content is executed.
- Output: React escapes all text; descriptions are rendered as text, never HTML. Logo URLs are never user-submitted and are rendered as `<img>` only.
- Headers: helmet on the API. For the static hosts, set a Content-Security-Policy such as `default-src 'self'; img-src 'self' data: https:; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src https://fonts.gstatic.com; connect-src 'self' https://api.example.com; frame-ancestors 'none'` (adjust `connect-src` to the API origin).
- CORS: allow-list only (`CORS_ORIGINS`); any localhost origin is allowed outside production only.
- Rate limits: global per minute, plus search/discovery, submissions (per 10 min) and login (per 15 min).
- Secrets: environment only; `.env` files are git-ignored; `VITE_*` are the only variables that reach browsers.

## Release checklist

1. `npm run lint && npm test` green; `npm run test:e2e` against a staging deploy.
2. Backup the database.
3. Deploy the API (migrations apply on start); confirm `/health/ready`.
4. Deploy the web build.
5. Smoke test: landing → enter → search → website → visit → back; review pending submissions.
